# Методика измерений

[English](benchmark-methodology.md) · [Русский](benchmark-methodology.ru.md)

Потоковый тест сравнивает непрерывный приём через прямой `ClientWebSocket.ReceiveAsync(Memory<byte>)` и `FastWebSocketClient`. Оба клиента получают одинаковые подготовленные JSON-фреймы от одного генератора. Стандартный клиент переиспользует приёмный массив; обработчик Pipelines считает сообщения, заимствуя их память без копирования. Здесь измеряется приём со счётчиками, без разбора JSON приложением.

Общий профиль в [streaming-profile.json](../scripts/streaming-profile.json): **128 байт полезной нагрузки, 20 фреймов на запись, 10 соединений, 5 с прогрева, 30 с измерения, три свежих процесса приёмника для каждого клиента**. Одна запись сервера содержит 2640 байт с заголовками WebSocket. Порядок клиентов чередуется между повторениями. Генератор проверяет маршрут с размером сообщения и batch при HTTP upgrade; несовпадение завершает запуск ошибкой.

```sh
# Генератор в отдельном процессе на этой машине; шесть свежих приёмников.
python3 scripts/streaming_benchmarks.py --output results/local/MY_STREAM
# Тот же приёмник, профиль, счётчики и порядок, но сервер на другой машине.
python3 scripts/streaming_benchmarks.py --url ws://GENERATOR-IP:5050 --output results/network/MY_STREAM
# Дополнительно измерить все четыре отдельных echo-сценария, последовательно.
python3 scripts/run-benchmarks.py --output results/local/MY_RUN
python3 scripts/render-results.py results/local/MY_RUN
```

Для сетевого запуска на другой машине нужен генератор с тем же профилем:

```sh
dotnet run -c Release --project benchmarks/WebSocketLoadTest -- \
  --mode server --listen 0.0.0.0 --port 5050 --payload-bytes 128 --batch 20
```

Без `--url` раннер запускает тот же сервер на свободном порту localhost, ждёт фактический адрес и сохраняет сервер на время всех шести приёмников. Он проверяет работу сервера, ограничивает время старта, измерения и остановки, отправляет команду штатного завершения и проверяет код выхода. Сбой любого процесса делает набор недействительным. CPU, управляемые аллокации и GC относятся **только к процессу приёмника**; сервер и Python-раннер исключены. В журнале сохранены команды и разные PID. Параметры `--count`, `--warmup`, `--duration`, `--runs`, `--payload-bytes` и `--batch` позволяют задать контрольный профиль; настройки двух сторон должны совпадать.

Прогрев исключён. Скорость — завершённые сообщения, делённые на фактическое время по монотонным часам. Существующий протокол снимает счётчики примерно раз в секунду; выделение памяти под метрики, планирование задач и вывод в консоль входят в счётчики процесса приёмника. Это не трассировка аллокаций самого транспорта. Постоянные затраты измерителя, поделённые на большее число сообщений, дают меньше байт на сообщение даже при прежнем поведении транспорта. В сводке сохранены полные и нормированные аллокации каждого повтора; 1 кБ = 1000 байт.


## Полный echo-обмен

Четыре случая BenchmarkDotNet: 128/4096 байт × Pipelines/адаптер ClientWebSocket, с побайтной проверкой ответа. Операция отправляет сообщение, ждёт возврата и проверяет его. Оба сетевых узла и асинхронный измеритель находятся в измеряемом процессе; стандартный адаптер тоже использует Pipe для callback API. Общие задачи, планирование и работа адаптера вносят вклад в аллокации. Близкое число байт на полный обмен не доказывает равенство аллокаций приёмного пути.

Echo остаётся отдельной нагрузкой: Release/x64, пять прогревочных и пятнадцать измерительных итераций с целевым временем 500 мс, один запуск. Погрешность — полуширина 99,9% доверительного интервала BenchmarkDotNet. Сохранены исходные значения, интервалы, GC, аллокации и полный stdout. Время итерации — целевое; обработка выбросов отражена в отчётах BenchmarkDotNet. Задержки хвоста отдельно не измеряются.

## Доказательная база и прежние измерения

Каждый новый набор содержит окружение, ревизию и SHA-256 исходников, хеши бинарников, точные команды дочерних процессов, samples, журналы и хеши артефактов. `render-results.py` проверяет весь сеанс и арифметику перед генерацией обеих README-таблиц. `verify-evidence.py` проверяет опубликованный набор, измеренные входы сборки, происхождение кода и неизменность исторических данных. Linux и Windows CI запускают общий раннер, оба клиента, штатное завершение сервера и очистку при сбоях.

Ethernet-матрицы от 8 ноября сохраняют исходные даты, код и манифесты. Основной компактный профиль также использовал 128 байт / 20 фреймов / 10 соединений / 5 с / 30 с и счётчики только приёмника. Библиотека по-прежнему задаёт приёмный TCP-буфер 64 KiB; автоматический размер — отдельный исторический контроль. Для новых физических Ethernet-результатов нужен повтор с текущим кодом и окружением. Прежние loopback-наборы по 87 байт с генератором в одном процессе остаются в архиве; их ресурсные счётчики не служат сопоставимым контролем нового streaming-теста.

Счётчики байтов и сообщений обновляются раздельно, байты — первыми. Снимок может застать одно обновляемое сообщение на соединение. Для двух снимков допускается консервативный сдвиг `2 × ClientCount × PayloadBytes`, в том числе в каждом интервале. Исходные значения не меняются; скорость считается по завершённым сообщениям.
